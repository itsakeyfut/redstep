# v0.7.0 — Declarative attack scenarios (DSL)

- **Version**: `v0.7.0`
- **Status**: planned
- **Theme**: Declarative attack scenarios (DSL)
- **Released**: —

> **In one sentence**: author attack scenarios declaratively — the entry point, the steps, the transitions, the expected outcome — in a DSL on top of the Rust core, so a scenario is data a reviewer can read and run, not only Rust a developer writes.

## Goal

The authoring model was settled as Rust first, DSL after: the Rust `#[security_test]` and the scenario builder came in the earliest releases, deliberately, because a DSL built before the capabilities and the multi-step chain existed would have been guessing at what it needs to express. Now that the capabilities, the vantages, and the multi-step chain are real, the DSL is worth adding: it lets a scenario be written and reviewed as declarative data, lowering the bar from "write Rust" to "describe the attack", and makes a scenario something a non-Rust reader can audit. The DSL compiles down to the same scenario and capability machinery, so it adds a way to express a scenario, not a second engine that could drift from the Rust one.

## Scope

- A declarative scenario DSL covering the attack-scenario vocabulary as data: the entry point and vantage, the steps, the network and privilege transitions, the expected outcome, and the attack path — realizes `ADR-0001`.
- The DSL compiles to the existing Rust scenario and capability machinery: a DSL scenario produces the same evidence and the same verdict as the equivalent Rust-authored one, so there is one engine, not two.
- A DSL scenario passes through the same safety gates as a Rust one: scope resolution, the intensity ladder, and the vantage model, with no path that constructs a target or a capability outside those gates — realizes `ADR-0006`.
- DSL errors are reported in the rustc-style the rest of the framework uses, with a location in the scenario source — realizes `ADR-0009`.

## Attack coverage

None. The DSL is an authoring surface; it adds no attack technique of its own, only a way to express the techniques that already exist.

## Out of scope

- New attack techniques or capabilities: the DSL expresses what exists, it does not add checks.
- Importing scenarios from other tools, and cloud/Windows-AD/AI scenarios — deferred to the later platform and adversary-emulation releases.
- A general-purpose programming language: the DSL stays a scenario description, not a Turing-complete language; anything it cannot express is still written in Rust.

## Depends on

v0.1.0 (the Rust scenario builder and the safety gates the DSL compiles down to and through), v0.5.0 (the multi-step chain the DSL's steps and transitions describe), and the capability set across v0.2.0-v0.4.0 that a scenario's steps invoke.

## Release criteria

- [ ] A scenario authored in the DSL runs and produces the same evidence and verdict as the equivalent Rust-authored scenario (a test compares the two).
- [ ] A DSL scenario is subject to the same scope, intensity, and vantage gates as Rust: a test proves an out-of-scope target or an unauthorized intensity in the DSL is refused, with no bypass.
- [ ] A malformed DSL scenario produces a rustc-style error with a location, not a panic or a silent default.
- [ ] The DSL is documented with worked examples covering a single-step and a multi-step scenario.
- [ ] The workspace version is bumped to 0.7.0 and the release is cut.

## Risks and open questions

- A new authoring surface is a new way to reach the capabilities, so it is a place a safety gate could be bypassed if the DSL constructs targets or capabilities by a different path. The DSL must go through the same scope and intensity gates as Rust; a target or intensity that the Rust path would refuse must be refused from the DSL too. This is the off-scale concern for this release and is guarded by routing the DSL through the existing gates rather than around them.
- Scope creep toward a general-purpose language: the DSL is kept to describing a scenario. The seam is "if it needs real logic, write Rust"; the DSL does not grow control flow to avoid that.
